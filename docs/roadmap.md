Этот документ фиксирует состояние рабочей копии, оставшиеся задачи и критерии готовности. Для запуска см. [README](../README.md). Для устройства брокера и версий запросов см. [архитектуру](architecture.md) и [контракт Kafka API](kafka-api.md). В этих двух документах часть разделов описывает целевой релиз. Фактические возможности сверяются по обработчикам, ответам `ApiVersions` и тестам.

## Цель и ограничения

- Rusta — лёгкий брокер с нативным Kafka Wire Protocol для небольшого VPS и распределённого кластера. Приоритеты по порядку — RAM, производительность, горизонтальное масштабирование, совместимость, надёжность, простота развёртывания. Корректность и сохранность подтверждённых записей обязательны при любой оптимизации.
- Основные компоненты на Rust. Собственный сегментированный append-only журнал, Tokio, Cargo, ограниченные буферы и backpressure. Без обязательных ZooKeeper, etcd, Redis, PostgreSQL, JVM или другого брокера в роли движка. Порядок гарантируется внутри партиции. Продюсер маршрутизирует ключи по правилам Kafka, а перенос реплик сохраняет идентификатор и порядок партиции.
- Поставлять релиз **только Docker-образами** для `linux/amd64` и `linux/arm64`, с Compose для локального запуска на Linux и MacBook через Docker Desktop. Один бинарник брокера внутри образа. README на английском.
- Минимальная прикладная модель — at-least-once с durable offset commits. Транзакции и exactly-once требуют отдельного решения. Кластер подтверждает `acks=all` после durable majority, single-node по умолчанию подтверждает durable local commit. Запись в page cache сама по себе подтверждением durability не считается. Ошибка или таймаут Produce допускают неизвестный результат. Повтор с idempotent producer проверяется по присвоенному offset.
- Начальные цели — 50–64 МиБ idle RSS single-node, желательно до 128 МиБ idle RSS на кластерную ноду, профиль 1 vCPU и компактный образ. Это цели для измерений. План должен учитывать RSS, heap, page cache, сетевые буферы и память на пике.

| Область | Что есть и чем проверено | Открытые ограничения |

| Single-node | Дисковый журнал, sparse indexes, offsets и timestamps, retention, topic creation, record batches, ключи, заголовки, пять режимов codec и idempotent retries. Classic groups сохраняют offsets, поддерживают eager и cooperative assignors и восстанавливаются после перезапуска. Smoke охватывает Java Kafka Client 4.1.2 и Spring Kafka 4.0.8. | 512 партиций, 128 TCP-соединений, batch до 1 МиБ. История ограничена 256 producer IDs на партицию. Нужна политика освобождения producer state. |
| Кластер | Отдельная Raft-группа контроллера и отдельный кворум каждой партиции, дисковый commit, Safe ReadIndex, mTLS на peer-сети. Java-тесты проверяют failover, сетевую изоляцию, отказ minority, топологии из 3 и 5 брокеров, RF3 и RF5. | До 128 партиций. Consumer работает с ручным назначением партиций. Журнал сохраняется без лимита retention. Восстановление реплик идёт из сохранённого Raft log. |
| Членство | Настраиваемый bootstrap и 1–255 заранее заданных ID. Присоединение заранее авторизованной ноды через learner. Decommission переносит реплики последовательно, сохраняет RF, передаёт лидерство, исключает ноду из контроллера. Проверены цикл 3 → 4 → 3 на Docker Desktop Apple silicon, SIGKILL контроллера в ходе переноса и доступность оставшегося кворума. | Peer inventory и сертификаты задаются заранее. Добавление меняет размещение новых топиков. Для автоматического перераспределения существующих партиций требуется отдельная работа. Decommission ожидает свободную реплику и доступные кворумы. |
| Протокол | Кластер рекламирует `ApiVersions`, `Metadata`, `CreateTopics`, `Produce`, `Fetch`, `ListOffsets`, `InitProducerId`, `OffsetForLeaderEpoch`. Single-node добавляет classic group API. Контракт содержит точные версии. | Кластерный Fetch сейчас возвращает доступные данные после read barrier. Нужна проверка long polling и семантики Fetch. Запланированные Admin API и клиенты Go, Python и Rust ещё предстоит проверить. |
| Поставка | Dockerfile с non-root образом и Compose-профили. Используются отдельные advertised listeners для хоста и Compose-сети. | Kafka listener PLAINTEXT, mTLS защищает межброкерный трафик. Полная CI, GHCR-релиз, Intel Mac и воспроизводимые Linux-замеры ещё впереди. |

- [Cluster Kafka dispatch](../crates/rusta-broker/src/cluster/kafka.rs), [состояние и движения реплик](../crates/rusta-broker/src/cluster/engine.rs), [Raft storage](../crates/rusta-broker/src/cluster/disk.rs), [peer transport](../crates/rusta-broker/src/cluster/transport.rs).
- [Java и Spring fixtures](../tests/java), [генераторы Compose и PKI](../scripts). Java-тестам нужны Docker Compose, host JDK 21 и Maven. Запускайте скрипты из корня последовательно, чтобы не конкурировать за порт, Docker-сети и образ `rusta:local`. Скрипты создают и удаляют собственные временные Compose-проекты.

```sh
git status --short --branch
cargo fmt --all -- --check
cargo test --workspace --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
tests/java/smoke.sh
tests/java/cluster-smoke.sh
tests/java/topology-smoke.sh
tests/java/membership-smoke.sh
tests/java/decommission-smoke.sh
```

Если Cargo отсутствует на хосте, на момент передачи проверки Rust выполнялись в том же образе toolchain, что указан в Dockerfile:

```sh
docker run --rm --mount type=bind,src="$PWD",dst=/workspace -w /workspace \
  -v rusta-cargo-registry:/usr/local/cargo/registry \
  -v rusta-cargo-target:/workspace/target \
  rust:1.100-bookworm bash -ec 'rustup component add rustfmt clippy
    cargo fmt --all -- --check
    cargo test --workspace --locked
    cargo clippy --workspace --all-targets --locked -- -D warnings'
```

Последний прогон decommission на момент передачи прошёл после изменений в Raft storage и передачи лидерства. Остальные кластерные smoke-тесты также проходили на этой итерации. Прогоны smoke на Mac проверяют реальное клиентское поведение и аварии контейнеров в одном физическом домене отказа. Для гарантий при потере питания и диска нужны отдельные Linux-испытания.

## Очередь работ до production-релиза

### 1. Распределённые classic consumer groups

Следующая задача. Переиспользовать семантику существующего координатора и Kafka-обработчики там, где она одинакова. Предлагаемое направление — стабильное отображение `group.id` на ограниченное число внутренних шардов, реплицируемых Raft, и ответ `FindCoordinator` с лидером нужного шарда. Подтверждать offset commit после durable majority. Новая эпоха координатора должна отсекать устаревшие операции. Rebalance, deadlines и таймеры должны приводить к согласованным переходам с новыми лидерами. Число шардов, способ их bootstrap, формат событий и необходимые гарантии чтения зафиксировать до реализации. Держать операции групп вне контроллера и пути записи пользовательских партиций.

1. Проверить зависимости и нарисовать последовательность `FindCoordinator → JoinGroup → SyncGroup → Heartbeat → OffsetCommit → OffsetFetch` для штатной работы и отказа.
2. Запустить Java `subscribe()` с commit и чтением с сохранённой позиции на трёх брокерах. Сделать вторым шагом rebalances, fencing, `LeaveGroup`, group Admin и оба предусмотренных формата `OffsetFetch`. Объявлять в `ApiVersions` только проверенные API и версии.
3. Прогнать Spring Kafka с двумя экземплярами consumer. Проверить убийство координатора до и после записи commit, сетевую изоляцию меньшинства, рестарт всех нод, повтор запроса, переход поколений и отсутствие потери подтверждённых offsets. Ожидаемая повторная доставка при at-least-once допустима.

### 2. Кластерное хранение и полнота data path

- Реплицировать продвижение log-start и применять `retention.ms`/`retention.bytes` по безопасным границам сегментов. Сохранить Kafka offsets, leader epochs и retry window продюсера. Проверить Fetch на удалённом диапазоне, timestamp lookup и настройки после смены лидера.
- Реализовать Raft snapshot/checkpoint, compaction consensus log и догоняющую репликацию после удаления старых записей. Зафиксировать формат, включить committed index/term, membership, retained range, метаданные и состояния идемпотентности/групп. Передавать чанками с лимитами памяти, диска и полосы. Тестировать оборванную установку, повреждение, повтор, дисковый сбой, параллельные запись и чтение и восстановление отстающей реплики.
- Уточнить cluster Fetch long polling, byte budgets, лидерские ошибки, retry после потерянного ответа и lifecycle producer state. Прогнать сценарии ротации сегмента, переполнения очереди, заполнения диска и потери части кворума. Сохранность подтверждённого префикса — критерий приёмки.

### 3. Эксплуатация кластера и миграция

- Добавить перераспределение уже существующих партиций после расширения, явный перенос лидерства и наблюдаемый статус relocation. Переиспользовать durable move plan и learner catch-up из decommission. Ограничить конкуренцию и трафик переносов. Проверить отмену или возобновление по согласованной модели, падение контроллера и ноды-назначения, повторные запросы и работу клиентов во время перебалансировки.
- Доработать регистрацию и изменения peer inventory для нод, не заданных при bootstrap, с проверкой node ID и mTLS. Согласовать способ выдачи и ротации сертификатов, контроль доступа к регистрации и управление кворумом. Проверить рост, удаление и повторный старт с теми же томами. Данные с retired node ID требуют явной процедуры.
- Сделать переход single-node → cluster с сохранением topic IDs, offsets, данных, producer state и group commits. Начальный вариант для оценки — управляемая миграция с остановкой записи, durable-фазами и fencing старого запуска. Проверить возобновление после сбоя на каждой фазе и документировать допустимые операции восстановления. Согласовать необходимую доступность во время миграции.

### 4. Совместимость и управление

- Довести матрицу из [контракта API](kafka-api.md), включая плановые `DeleteTopics`, `DescribeConfigs` и `IncrementalAlterConfigs`. На поддерживаемых версиях проверить повторы админских операций, validate-only, корректную очистку данных и ошибки для неподдерживаемых настроек. Уточнить возможность расширения партиций отдельно от переноса реплик.
- Зафиксировать версии franz-go, confluent-kafka Python и rust-rdkafka и прогнать create/list/describe, produce/fetch, idempotent retry, groups/offsets, лидерскую смену и fallback negotiation. Выпускать матрицу с конкретными версиями и сценариями. Java 4.1.2 и Spring Kafka 4.0.8 — базовые регрессии.
- Покрыть неподдерживаемые запросы, schema limits, гибкие заголовки, разные версии ApiVersions и сценарии с обеих advertised сетей. Не выдавать успех для незавершённых операций.

### 5. CI, поставка и эксплуатационная документация

- Добавить GitHub Actions для rustfmt, Clippy, unit и integration tests и Docker smoke. Отдельные долгие fault и benchmark прогоны. Закрепить toolchain и зависимости для повторяемой сборки, синхронизировать фактический MSRV с Cargo и CI.
- Собрать версионированный multi-platform Docker-образ в GHCR. Проверить `linux/amd64` и `linux/arm64`, Compose на Apple silicon и Intel Mac, non-root, именованные тома и запуск без внешних сервисов. Проверить build/install по истории релизов и обозначить обновления, которые требуют остановки кластера.
- Подготовить English README, примеры Java/Spring, матрицу API, настройки, руководство по обновлению, масштабированию, мониторингу, backup/restore и инцидентам. Документировать режим клиента PLAINTEXT и реальные границы безопасного развёртывания. Согласовать профиль клиентской безопасности перед публичным production-релизом.

### 6. Нагрузка, измерения и критерии релиза

- Сравнивать с Apache Kafka, Redpanda, Apache Iggy и релевантным лёгким брокером, например NATS JetStream. Зафиксировать версии/дижесты, скрипты, аппаратную платформу, файловую систему, конфиги, прогрев и повторы. Для брокеров с другими протоколами описывать сценарий и отличия API.
- Сопоставлять профили RF1 и RF3 по оборудованию, batching, ACK, числу durable копий и sync-политике. Отдельно маркировать профили, где гарантии выровнять невозможно. Не сравнивать запись в page cache с durable ACK.
- Замерять idle RSS, RSS под нагрузкой, peak RSS, heap, page cache, сетевые буферы и cgroup peak, CPU, messages/s и MB/s, p50/p95/p99, disk I/O, startup, recovery, скорость репликации и поведение при добавлении нод. Варьировать размер сообщения, число топиков, партиций, producers и consumers. Измерить размер release-образа и бинарника.
- Опубликовать измерения с условиями и сырыми результатами. Сначала пройти fault-тесты и проверить сохранность подтверждённых сообщений и offsets. При промахе по RAM объяснить причины и измерить достижимый бюджет. Рассматривать mmap, io_uring или zero-copy только с подтверждённой выгодой.

## Решения, которые остаются за владельцем

Перед изменением объёма отдельно обсуждать transactions, exactly-once, log compaction пользовательских топиков, tiered storage, SASL и другие способы аутентификации, ACL, quotas, Kafka Connect, Kafka Streams, Schema Registry, multi-tenancy, расширенные Admin API, старые версии Kafka и сложные политики размещения/хранения. Техническая компактация Raft после снапшота относится к кластерному хранению и рассматривается отдельно от Kafka log compaction.

Для каждой функции зафиксировать нужный сценарий и распространённость с источниками, последствия отсутствия, цену в RAM/CPU/latency, сложность реализации и возможность добавить её позже. Если конкретная версия клиента зависит от функции, указать запрос, путь fallback и проверенный результат. Решение о включении или исключении принимает владелец проекта.
